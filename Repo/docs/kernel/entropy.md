# Native entropy API

`src/kernel/entropy.c` implements `syscall_do_getrandom`, the kernel side of
`sys_getrandom(buffer, length, flags)`. The libc interfaces are declared in
`<sys/random.h>` and implemented in `user/lib/random.c`.

The backend uses the current CPU's x86-64 `RDRAND` instruction. Each nonempty
call checks CPUID leaf 1, ECX bit 30 before executing that instruction. It accepts
a word only when the instruction sets the carry flag, including when the word
itself is zero. A word gets at most ten attempts. There is no clock-derived
seed, fixed seed, software PRNG, or successful fallback for unavailable hardware.
These checks follow Intel's documented [feature detection, carry flag contract,
and bounded retry guidance](https://www.intel.com/content/www/us/en/developer/articles/guide/intel-digital-random-number-generator-drng-software-implementation-guide.html).

## API behavior

| Interface | Result |
| --- | --- |
| `sys_getrandom(buffer, length, flags)` | At most 256 generated bytes, or a negative errno. Requests larger than 256 return a short read. |
| `getrandom(buffer, length, flags)` | The actual byte count, or `-1` with thread-local `errno`. |
| `getentropy(buffer, length)` | Fills up to 256 bytes, returning 0. Loops over short reads and retries `EINTR`. Larger requests fail with `EIO`. |

Only flags 0 and `GRND_NONBLOCK` (1) are supported. Unknown bits fail with
`EINVAL`, including for an empty request. An empty request with valid flags
succeeds without accessing a buffer or requiring RDRAND. Unavailable hardware
returns `ENOSYS`; exhausted retries return `EIO`, or `EAGAIN` with
`GRND_NONBLOCK`. Allocation failure returns `ENOMEM`; an inaccessible output
buffer returns `EFAULT`.

Generation completes in a private kernel heap buffer before copyout begins, so
hardware failure cannot expose partially generated or uninitialized heap bytes.
Copyout uses the shared permission-checked user-copy implementation. A fault on
a later output page can leave a generated prefix, as documented by that
implementation. The temporary allocation is wiped before being freed on both
success and failure.

Preemption is suppressed from the per-CPU feature check through allocation,
generation, copyout, wiping and release. This prevents CPU migration between
feature detection and execution, and prevents process cancellation from
stranding heap ownership on a discarded kernel stack. Interrupts remain enabled
apart from the existing short allocator/user-copy critical sections. There is
no blocking wait or cross-thread stack pointer. The generation work is bounded
to 256 bytes and at most 320 instruction attempts per syscall.

## QEMU backend and validation limits

For QEMU 10.1.2 under TCG, the upstream
[`HELPER(rdrand)` implementation](https://github.com/qemu/qemu/blob/v10.1.2/target/i386/tcg/int_helper.c)
obtains bytes through `qemu_guest_getrandom`. Its
[guest random implementation](https://github.com/qemu/qemu/blob/v10.1.2/util/guest-random.c)
uses `qcrypto_random_bytes` in the normal mode. QEMU's explicit seeded/replay
modes change that behavior; acceptance runs must not use `-seed` or record/replay
randomness. The default TCG CPU needs the `+rdrand` feature for this API; a
separate `-rdrand` run verifies the unavailable-backend path. Physical CPU and
hypervisor entropy implementations remain the source of the returned bytes.

`python3 tests/entropy_contract_test.py` runs the production retry, allocation,
copyout and libc wrapper functions under ASan/UBSan with controlled hardware
responses. It checks successful zero values, exhausted/late failures, no output
on generation failure, all cleanup paths, allocation bounds, copied prefixes,
and short-read handling. Hardware instruction boundaries are simulated in this
host test.

`tests/entropy_test.c` is the native acceptance fixture. Its normal mode checks
argument errors, unaligned short reads, read-only/PROT_NONE/unmapped output,
and 64 full samples on each of eight pinned CPUs. Its `unsupported` argument
requires RDRAND to be disabled and checks `ENOSYS` without output modification.
The required success markers are:

```
ENTROPY_TEST: PASS workers=8 cpu_mask=0xFF samples=512
ENTROPY_TEST: unsupported PASS
```

The sample comparisons catch constant or repeated output. They do not establish
cryptographic quality; that relies on the documented source backend, not a
diversity test.
